# OOP Principles in Safari Smart — Presentation Notes

## 1. Encapsulation (Data Hiding)

**Where**: All model classes — `User.java`, `Booking.java`, `Payment.java`, `SafariPackage.java`, `Category.java`

**Example** — `src/main/java/com/safarismart/safarismart/model/User.java`:
```java
@Entity
@Table(name = "users")
@Data
@Builder
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;           // private — hidden from outside

    @Column(unique = true)
    private String email;      // private — hidden from outside

    private String password;   // private — hidden from outside

    @Enumerated(EnumType.STRING)
    private UserRole role;     // private — hidden from outside
}
```

**Why it's Encapsulation**:
- All fields are `private` — cannot be accessed directly from outside the class
- Access is controlled through public **getters** (read) and **setters** (write) generated by Lombok's `@Data`
- Example: `user.getEmail()` to read, `user.setName("John")` to write
- The internal representation is hidden — if we change how `password` is stored (e.g., add salt), external code doesn't break

**Say to teacher**: "Data is wrapped inside the object. Other classes can't touch the fields directly — they must go through methods."

## 2. Inheritance (Code Reuse)

**Where**: All repository interfaces

**Example** — `src/main/java/com/safarismart/safarismart/repository/BookingRepository.java`:
```java
public interface BookingRepository extends JpaRepository<Booking, Long> {
    List<Booking> findByUserId(Long userId);
    List<Booking> findByStatus(BookingStatus status);
}
```

**Same pattern in**: `UserRepository`, `SafariPackageRepository`, `PaymentRepository`, `CategoryRepository`

**Why it's Inheritance**:
- `JpaRepository<Booking, Long>` is the **parent class** — it already provides:
  - `findAll()` — get all records
  - `findById(id)` — get one record
  - `save(entity)` — insert or update
  - `deleteById(id)` — delete a record
  - `count()` — count records
- `BookingRepository` **inherits** all these methods automatically without writing any code
- We only add custom methods like `findByUserId(Long userId)`

**Say to teacher**: "Child classes inherit ready-made database methods from the parent. We only write the queries that are special to our needs."

## 3. Polymorphism (Many Forms)

Polymorphism means "many shapes" — the same method name doing different things.

### Example A: @PrePersist (Same annotation, different behavior)

**`Booking.java`**:
```java
@PrePersist
protected void onCreate() {
    createdAt = LocalDateTime.now();
    status = BookingStatus.PENDING;
    if (safariPackage != null && numberOfPeople > 0) {
        totalAmount = safariPackage.getPrice()
            .multiply(BigDecimal.valueOf(numberOfPeople));
    }
}
```

**`Payment.java`**:
```java
@PrePersist
protected void onCreate() {
    paymentDate = LocalDateTime.now();
    status = PaymentStatus.PENDING;
}
```

Both use `@PrePersist` — same annotation name — but Booking calculates `totalAmount` while Payment doesn't. **Same interface, different implementation.**

### Example B: Method Overloading in `UserService.java`

```java
public User saveUser(User user) { ... }                        // 1 — save existing
public User findOrCreateUser(name, email, phone) { ... }       // 2 — find or create new
public User registerAdmin(name, email, phone, password) { .. } // 3 — create admin
```

**Same concept** (creating/retrieving a user) but with **different parameters** and **different internal logic**.

**Say to teacher**: "The same method name can do different things depending on what you pass to it, or which object calls it."

## 4. Abstraction (Hiding Complexity)

**Where**: Service layer — `BookingService.java`, `PaymentService.java`, `UserService.java`, etc.

**Example** — `src/main/java/com/safarismart/safarismart/service/PaymentService.java`:
```java
public Payment createPayment(Booking booking, String paymentMethod) {
    String receiptNumber = "RCP-" +
        LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyyMMdd"))
        + "-" + UUID.randomUUID().toString().substring(0, 8).toUpperCase();

    Payment payment = Payment.builder()
            .user(booking.getUser())
            .booking(booking)
            .amount(booking.getTotalAmount())          // auto-calculated
            .paymentMethod(paymentMethod)
            .receiptNumber(receiptNumber)               // complex generation
            .status(PaymentStatus.PENDING)
            .build();

    return paymentRepository.save(payment);
}
```

**What the Controller sees** (in `PaymentController.java`):
```java
@PostMapping("/save")
public String savePayment(...) {
    Booking booking = bookingService.getBookingById(bookingId);
    paymentService.createPayment(booking, paymentMethod);  // one clean call
    return "redirect:/payments/receipt/" + bookingId;
}
```

**Why it's Abstraction**:
- The controller calls `paymentService.createPayment(...)` — one line
- Behind that one line: receipt generation, amount calculation, status setting, database save
- The controller doesn't need to know ANY of that complexity

**Another example** — `BookingRepository` interface:
```java
List<Booking> findByUserId(Long userId);
```
Spring Data JPA reads this method name and **automatically writes**:
```sql
SELECT * FROM bookings WHERE user_id = ?
```
The developer only declares **what** they want — Spring handles **how** to do it.

**Say to teacher**: "We hide the difficult implementation details behind simple method calls. The controller just says 'create payment' — the service handles all the receipt generation, amount calculation, and database work."

## 5. Interfaces vs Abstract Classes

### Interface — Used everywhere in this project

**Definition**: A contract that says "any class that implements me MUST have these methods."

**In this project**: All 5 repositories are interfaces:

```java
public interface PaymentRepository extends JpaRepository<Payment, Long> {
    Optional<Payment> findByReceiptNumber(String receiptNumber);
    boolean existsByBookingIdAndStatus(Long bookingId, PaymentStatus status);
}
```

**Analogy**: Like a **menu** at a restaurant:
- The menu lists what's available (findByReceiptNumber, save, delete) — the **contract**
- You don't need to know how the kitchen cooks — the **implementation** is hidden
- You could swap the kitchen (switch from PostgreSQL to MySQL) and the menu stays the same

### Abstract Class — NOT in this project (hypothetical example)

**Definition**: A class that is partially built — some methods are fully coded, others are just declared (abstract) and must be implemented by subclasses.

**Hypothetical example** of what COULD be in the project:

```java
public abstract class BaseEntity {
    private Long id;
    private LocalDateTime createdAt;

    public Long getId() { return id; }        // concrete — already works

    public abstract String getSummary();      // abstract — subclasses MUST do this
}

// Each subclass provides its own version:
public class Booking extends BaseEntity {
    public String getSummary() {
        return "Booking #" + id + " for " + safariPackage.getName();
    }
}

public class Payment extends BaseEntity {
    public String getSummary() {
        return "Payment " + receiptNumber + " - $" + amount;
    }
}
```

### Key Difference Table

| Feature | Interface | Abstract Class |
|---------|-----------|---------------|
| Methods | ALL are unimplemented (contract only) | Can have BOTH implemented AND unimplemented methods |
| Multiple | A class can `implement` MANY interfaces | A class can `extends` only ONE abstract class |
| Fields | Only `public static final` constants | Can have instance fields (like `id`, `createdAt`) |
| Relationship | "What it CAN DO" (behavior contract) | "What it IS + what it DOES" (partial implementation) |
| Example in project | `PaymentRepository extends JpaRepository` | Not used, but could be `BaseEntity` |

## Quick Summary for Teacher Q&A

| OOP Principle | Where in Project | One Sentence Answer |
|---------------|-----------------|-------------------|
| **Encapsulation** | All Entity classes (`User`, `Booking`, `Payment`) | Fields are private, accessed only through getters/setters |
| **Inheritance** | All Repository interfaces extend `JpaRepository` | Child gets parent's database methods for free |
| **Polymorphism** | `@PrePersist` in Booking vs Payment; method overloading in services | Same method name, different behavior depending on the object |
| **Abstraction** | Services hide DB logic from Controllers | Controllers just call `service.method()` without knowing the complex internals |
| **Interface** | Repository interfaces are pure contracts | Spring reads method names and auto-generates SQL — we only say WHAT, not HOW |
| **Abstract Class** | (Not in project) | A partial implementation — some methods ready, some left for children to fill |
